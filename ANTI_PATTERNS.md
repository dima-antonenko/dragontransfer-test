# Антипаттерны

То, что ломает границы проекта. Если задача явно требует обратного — сначала обновить `DECISIONS.md`.

## Границы слоёв

**Бизнес-логика в контроллере или в колбэке модели.**
Создание заявки, синхронизация, разбор webhook и нормализация телефона живут в `app/services`.
Контроллер не вызывает `Faraday` и не собирает тело `orders/create`.

**HTTP партнёра внутри сценария.**
`Orders::*`, `Precalcs::*`, `Rates::*` ходят наружу только через переданный `client`.
Новый путь Partner API добавляется методом `DragonTransfer::Client`, а не разовым `connection.post` в сервисе.

**Прямой вызов Partner API из браузера.**
`miniapp.js` знает только `/api/*` и `/orders/:id`. Ключ, базовый URL партнёра и форма конверта
`{ success, payload }` во фронт не протекают.

## Секреты и доверие

**Ключ в JS, ERB, фикстурах репозитория или логах.**
`DRAGONTRANSFER_API_KEY` читается на сервере. В логи он попадает под фильтр `:api_key` и `:_key`.
Не печатать заголовок `X-Api-Key` в info-логе.

**Своё сравнение ключа webhook.**
Только `DragonTransfer.valid_api_key?`. Обычный `==` и сравнение без проверки длины
дают тайминг и принимают пустой ключ, если ENV не задан.

**Считать `telegram_user_id` аутентификацией.**
Значение приходит из тела запроса (`initDataUnsafe` на клиенте). Подпись `initData` не проверяется.
Нельзя закрывать им доступ к чужой заявке, выдавать права или искать заказы «текущего пользователя».
Пока нет проверки подписи, id заявки — единственный ключ экрана статуса, и он не секретный.

**Отдать в JSON лишнее.**
`as_api_json` не включает `raw_payload` и ключ. Не расширять ответ сырым payload партнёра.

## Заявка и статусы

**Путать `id` и `external_id`.**
Return URL, опрос UI и `Orders::Show` используют локальный integer.
Webhook и `orders/find` используют UUID партнёра.

**Откатывать статус вручную.**
Не присваивать `order.status =` в обход `apply_remote_payload!`. Ранг существует,
чтобы поздний `PENDING` не затирал `PAYIN_SUCCESS`.

**Ходить в `orders/find` для финала или черновика без `external_id`.**
Это уже отсекает `Orders::SyncStatus`. Не дублировать опрос в контроллере «на всякий случай».

**Оставлять локальную строку, если `orders/create` упал.**
`Orders::Create` удаляет её и пробрасывает ошибку. Глотать `DragonTransfer::Error` и показывать
черновик `NEW` без `external_id` нельзя: пользователь не сможет пройти KYC.

**Считать деньги через Float.**
Суммы — строки и `BigDecimal`. Не писать `amount.to_f` в атрибуты `Order`.

**Менять валюту или сеть в обход модели.**
Первый этап — RUB → USDT TRC20. Адрес вне `Order::TRC20_ADDRESS` не сохраняется.

## Продукт, которого нет

**Telegram-бот.**
Не добавлять webhook Bot API, long polling, handlers команд и inline-режим.
Telegram в этом репозитории — Mini App и опциональная тема.

**Очереди, фоновые джобы, Action Cable для статуса.**
Статус обновляют webhook и опрос раз в 20 с. Sidekiq, Redis и канал «order status»
не заводятся без отдельной задачи.

**Учётки, Devise, Pundit, Blueprinter.**
Их нет. JSON собирает `as_api_json`. Права на заявку не проверяются политикой,
потому что пользователей нет (см. решение 10).

## Тесты и репозиторий

**Реальный HTTP в спеке.**
Клиент — `instance_double`, сеть закрыта WebMock. Не ходить на `test.dragontransfer.online` из RSpec.

**Новые примеры в `test/` или закомментированные спеки.**
Канонический набор — `spec/`.

**Коммит `.env`, `config/master.key`, `.kamal/secrets`.**
Образец переменных — `.env.example` с плейсхолдером вместо ключа.

**Обход CI-проверок.**
Brakeman, bundler-audit, RuboCop и RSpec уже в `.github/workflows/ci.yml`.
Не отключать их флагами, чтобы «починить» красный прогон.
